GAMEWORLD: guard unsynthesized SPURS +0x18 chain in 3 state handlers

After the game-world init completes, the SPURS state machine func_000379BC
advances into a family of state handlers (func_000352F8, func_00035390,
func_000354C4) that follow the struct slot [0x27F7F4+0x18] = [0x27F80C] - a
SPURS object/workload chain. We synthesize the +0x20/+0x28 chains
(0x27F814->0x70B000, 0x27F81C->0x70A000) but never the +0x18 one, so it is 0;
the handlers deref null -> read low memory -> a garbage OPD (0x900A0000) ->
read AV. These handlers dispatch a workload vtable method (status/reporting);
with our faked SPURS they can't do real work.

Guard (all #ifdef GAMEWORLD_REAL_INIT, so baseline byte-identical): when
[0x27F80C]==0, undo the off-by-4 wrapper's stdu and return r3=0. With the three
guards the GAMEWORLD path no longer AVs and runs much further - 15 threads spawn
(SDU workers, audio cri_adxm_*, Terminate Thread; up from 8) - until the game's
own assertion handler func_000D91E4 fires (syscall 988 r3=4) and the process
shuts down cleanly. So the new blocker is a game-side abort, not a crash.

Baseline-safe: 221102 lines, all threads finished. (Alternative to guarding each
handler: synthesize a valid [0x27F80C] chain with a no-op OPD so the handlers run
returning status 0 - may avoid the later assert; deferred.)
