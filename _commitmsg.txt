Fix load-with-update (ldu/lbzu) in strcmp func_000D26C4 - clears thread-reg hang

func_000D26C4 is the C-library strcmp (SWAR word-at-a-time). Its inner loops read
[r3+8]/[r4+8] (doubleword) and [r3+1]/[r4+1] (byte tail) with FIXED offsets and
never advance r3/r4 - the original instructions were ldu/lbzu (load-with-update)
and the lifter dropped the base-register advance. So strcmp of two strings that
match past the first 8 bytes (no embedded NUL) spins forever.

This hung the game-world thread registration: func_0003A4D4 -> func_000103A4 ->
func_000103A8 (a name->handler hash insert) strcmp's the orchestration-thread
names ("Initialize Thread"/"Regist Context Thread"/"Unlock Thread", keys
0xF3C04/0xF3C0C/0xF3C14) and looped on the first long match.

Fix: advance the pointers as ldu/lbzu do (r += stride; load [r]). With it, all
three thread registrations complete and the whole game-world init sequence runs
to the end (func_00034288 -> 3x func_000103A4 -> func_00019B84 -> func_000356C0),
returning to the SPURS state machine func_000379BC which advances to a new
blocker (read AV at 0x900A0004 in func_000352F8).

NOTE: load-with-update is a SYSTEMATIC lifter bug (upstream-fixed); it cannot be
regex'd surgically (ldu is indistinguishable from ld in the emitted C), so this
is a targeted fix of the strcmp that blocks the menu path. The clean global fix
is the re-lift (EVENT_CYCLE_PLAN Phase 1 Option B). Baseline-safe: 221102 lines,
all threads finished (2 runs).
