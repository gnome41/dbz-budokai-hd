Fix systematic float-compare NaN handling (fcmp/fcmpu) - 1435 sites

The lifter emitted every floating compare as
  cr_val = (a < b) ? 8 : (a > b) ? 4 : 2
i.e. FL(<)=8, FG(>)=4, else FE(=)=2. For a NaN operand a<b and a>b are both
false, so it fell through to 2 (EQUAL) - but PPC fcmpu/fcmpo set FU (unordered)
= 1 for NaN, not equal. Result: every NaN-detection branch in the game was
defeated (a value compared with itself is unordered iff NaN; the game uses this
idiom after sqrt/div to call its NaN handlers).

Fix via _apply_fcmp.py: the trailing `: 2;` becomes `: (a == b) ? 2 : 1;` so NaN
yields FU=1. Non-NaN values are unchanged (a==b is true in the else); integer
compares use `int64_t a` and are not matched. Baseline-safe: 221102 lines, all
threads finished (the NaN path is not exercised by the default build).

Found while tracing the GAMEWORLD dtoa hang: func_00068998 does `fcmpu f0,f0`
after a sqrt to detect NaN and call func_000E14E4; the buggy compare reported
"equal" so the handler was skipped. (This particular hang has a second, separate
cause - a float-store/double-read mismatch in the number formatter defeating its
Inf/NaN classifier - still open.)
